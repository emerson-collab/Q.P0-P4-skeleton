Purpose
Add multi-Capability active mount-set realization while preserving one exact Provider Capability per immutable P2 mount, and retire Q.SS.STD.META.CONTRACT.DATABASE_PERSISTENCE as a normative P2 dependency.

Preserved P2 boundaries
- One P2 Stage and exactly two parallel role profiles remain: Provider and Consumer.
- The five existing P2 Capabilities remain unchanged.
- Receiving repository local P0 remains the only execution Runtime.
- Provider publication preserves one exact Capability Contract ref/hash; one mount binds one Provider Capability only.
- P2 Stage owns zero database objects and no business semantics, Gate verdict, Activation authority or Workflow execution authority.
- Direct cross-Domain SQL, cross-owner foreign keys, adapter/bridge/wrapper/second-runtime substitution remain forbidden.

V0120 mount-set lifecycle
- Consumer external_capability_mounting adds exactly two Operations: create_mount_set and activate_mount_set.
- Exact P2 Operation count advances from 15 to 17; exact physical Stage path count advances from 52 to 56.
- create_mount remains the immutable per-Provider-Capability mount constructor and exact readback remains required.
- create_mount_set composes one or more retained mounts for the same receiving Domain, requires unique Provider Capability Contract refs, canonical member ordering and a deterministic mount_set_hash.
- activate_mount_set re-verifies every member mount and implementation binding, then switches active_mount_set_pointer atomically last.
- activate_mount is retained as singleton-mount-set compatibility behavior and resolves to the same canonical active mount-set pointer model.
- Restart recovery reads active_mount_set_pointer first, then the retained mount set, every member mount and every immutable implementation binding; any missing or mismatched element FAILS_CLOSED.
- execute_mounted_capability resolves exactly one Provider Capability member from the active mount set and binds both mount_set_hash and selected mount_hash into the deterministic execution receipt.
- No mount-set member implicitly authorizes or invokes another Provider Capability.

Persistence boundary
- Q.SS.STD.META.CONTRACT.DATABASE_PERSISTENCE is not a normative dependency of P2 V0120.
- Durable mount, mount-set and active mount-set pointer state is owner-local state of the exact receiving Domain and is physically realized by that repository Skeleton/runtime.
- P2 defines lifecycle invariants only; it does not own physical table names, storage technology or Stage-level database objects.
